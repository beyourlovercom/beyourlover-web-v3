## 2. P2.1 — Thank You / order-received

**Required states** (driven by actual Woo order and payment evidence):
1. **Paid/processing/completed:** legitimate order confirmation, real Woo order number, amount, shipping summary, next action and clear estimated communications only where configured.
2. **Pending/on-hold/unpaid:** explicitly say payment is not yet confirmed; do not show a false success icon or shipment promise; surface order-pay/retry only when Woo permits.
3. **Failed/cancelled/refunded:** show correct status and supported next action; no automatic second charge.
4. **Missing/invalid order key, forged URL or unauthorized order:** do not disclose order/customer PII or treat guessed IDs as valid. Rely on Woo's canonical access, order key and owner verification.
5. **Guest vs signed-in:** correct account continuation without forcing account creation; access to order detail remains owner/key-gated.
6. **No checkout order exists on Dev:** render an honest empty/return-to-cart state; **never create synthetic payment success just for screenshots**.

Layout proposal for Owner visual review: restrained Apple-like confirmation shell, one status/title block, real order summary, delivery/communication note, tracking entry and account action. New design must obtain **Owner visual PASS** before theme implementation. Do not create a competing payment/fulfillment authority or inject tracking timestamps absent from evidence.

## 3. P2.2 — My Account, Orders and Order Detail

Reuse core Woo `my-account`, `orders`, `view-order`, `order-pay` URLs, hooks and auth checks. Provide order totals, date, payment state, fulfillment state (only when actually available), shipping address, line items, tracking if projected, support/help entry and permitted retry-payment action. Handle guest, owner, expired key, logged-out, pending, failed and completed states. **Split shipments** require package-level tracking rather than overwriting order-wide tracking. Do not expose order data via public REST or URL ID alone.

## 4. P2.3 — Tracking and AfterShip

Keep `/track-your-order/` as the existing Woo order-status lookup until proper shipment projection is verified. ERP Shipment owns carrier, reference and fulfillment events; Woo displays an authorized projection of package/carrier/tracking details. AfterShip is optional event visualization only after real installation/contract audit; don't add a second source of shipment truth or fake statuses. Test multi-package, missing carrier, stale tracking, out-of-order webhook and idempotent projections. Plugin addition or new ERP write needs its own scope gate.

## 5. P2.4 — Transactional Email and transport

Inventory and map order receipt, paid/processing, failed-payment, refund, shipment and delivery notices across Woo, existing template plugins, mail transport, ERP, AfterShip and future Andy Email OS. One recipient intent should produce one canonical email event; do not double-send shipping notifications. Dev outbound `pre_wp_mail` interception must remain until an explicit isolated mail UAT; do not treat template `enabled=yes` as evidence an email was delivered.

## 6. P2.5 — Failed-payment recovery

Use Woo `order-pay` for eligible existing unpaid orders when authorized, not an unconditional new Woo order. Respect ERP Payment Authority, pending/hold checks and stale-pending reconciliation. No automatic gateway retry after issuer decline, duplicate attempt or erroneous shipment trigger. Check token expiry, cancelled/refunded statuses and idempotency.
