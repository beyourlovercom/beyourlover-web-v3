## P5 hardening: Store API Checkout pathway (2026-10-08)

**Finding:** the existing MU guard's `woocommerce_checkout_process` hook is a *classic checkout* path only. WooCommerce Store API uses `/wc/store/v1/checkout` (also a versionless route). Official WooCommerce developer guidance says `GET /checkout` can create a checkout-draft order, and Store API processing hooks differ from classic shortcode hooks. **This is a missing protection path in the previous source, not evidence of an observed unauthorized order.**

**Proposed GitHub-only fix (not yet deployed to Dev):**
- On the staging site only, `rest_pre_dispatch` denies all methods except `OPTIONS` for `/wc/store/v1/checkout` and `/wc/store/checkout` when the *existing* short-lived `byl_dev_p13_checkout_gate()` permit is absent/invalid.
- Returns structured HTTP 403 before the Store API checkout route can create a draft/order or process a transaction; preserves pre-existing REST errors, and does not interfere with cart/coupon endpoints or native address autocomplete.
- Reuses the original permit/identity/test-mode checks without writing tokens or creating a session. The enabled permit does not guarantee *all* business isolation: ERP/AfterShip outbound handling and synthetic checkout outcome remain separately gated.
- Adds a standalone PHP negative-path test to Foundation verification: no-config gateway closure, Store API GET/POST/HEAD/PUT/PATCH/DELETE denial for both route forms, OPTIONS and unrelated routes unaffected, email blocked, classic Checkout notice, noindex/nofollow/noarchive.
- **This is an offline/stubbed negative-path test**, not a live WordPress REST integration test. Before Dev deploy: confirm exact MU source parity, staging identity, private backup, environment guard; after Dev deploy: repeat read-only `GET /wp-json/wc/store/v1/checkout` and `OPTIONS` checks using an isolated synthetic browser session, check for no unauthorized HPOS draft order increase; test no-credentials/expired/wrong-user/wrong-cookie controls without exposing secrets; ensure public classic Checkout and native autocomplete remain functional.
- Do **not** create the private temporary permit, attempt privileged login/session creation, submit a test order, or touch WWW/Live until the separate supported test-session workflow is authorized and workable.
