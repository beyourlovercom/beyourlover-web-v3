## 1. Existing ERP outbound architecture — REUSE, do not rebuild

`WooCommerceTrackingOutboundService::prepare` derives an outbox intent per Shipment:
- Root order `source_type=woocommerce` and exact external reference for the gateway's `connection_key`, otherwise fail closed.
- Shipment must be `shipped`, with `carrier`, `tracking_number`, `shipped_at` present.
- All package lines require exact positive `woocommerce_line_item_id` and quantity; no SKU inference.
- Carrier must have an explicit alias → `aftership_slug` in ERP config.
- Unique idempotency fingerprint includes **connection key, provider order, shipment ID, slug, tracking number, ship date and bound item IDs/quantities**.
- Outbox manages claim/retry/terminal remote conflict and marks complete **only after verified remote readback**; then runs ERP manual-sync completion and Woo order-status outbound as a **separate consequential action**. Do **not** launch a tracking canary without inspecting the follow-on status mutation and notification effects.

`HttpWooCommerceTrackingGateway` targets `{services.woocommerce.url}/wp-json/wc/v3/orders/{id}` using Woo credentials. It GETs existing order metadata, computes the new package, then **PUTs Woo REST `meta_data`** and reads back to verify. It preserves existing package IDs, rejects conflicting carrier/number, duplicate package ID, or an existing Woo line claimed by another package.

**Schema mapping** (verified against installed AfterShip plugin reader):
| ERP source | Woo REST meta | AfterShip reader |
| --- | --- | --- |
| Shipment carrier resolved through explicit mapping | `_aftership_tracking_items[].slug` | `$item['slug']` → courier by slug |
| Shipment `tracking_number` | `_aftership_tracking_items[].tracking_number` | tracking number |
| `md5(slug . '-' . tracking_number)` | `_aftership_tracking_items[].tracking_id` | package lookup identity |
| Shipment `shipped_at` UTC date | `_aftership_tracking_items[].additional_fields.ship_date` | supplemental tracking data |
| Exact Woo line identity/qty | `_aftership_tracking_items[].line_items[]` | stored package binding; not a new order authority |
| Legacy single-package summary | `_aftership_tracking_number`, `_aftership_tracking_provider_name` | backward-compatible first package fallback |

AfterShip plugin `get_tracking_items()` reads `WC_Order->get_meta('_aftership_tracking_items', true)` under Woo 11.x/HPOS and `display_tracking_info` hooks Woo `woocommerce_view_order` for an authenticated successful order lookup. This matches the metadata producer **at the field-shape level**, not yet at the end-to-end API/write level.

### Separate inbound delivery-evidence lane

`DeliveryEvidenceIngestService` is a separate **carrier status evidence reader**; ERP's DI currently binds `DeliveryEvidenceGateway` to **AfterShipBrandedPageDeliveryEvidenceGateway**. Delivery evidence `preview` vs `apply` uses status parsing/fingerprint/database locks and can lead to aggregate Woo status updates. **Never mistake this inbound evidence lane for ERP → Woo tracking-number writes.** No live branded-page/API inspection was performed.

## 3. Multipackage & fail-closed semantics — CONDITIONAL

Existing ERP gateway tests on main document:
- Distinct Woo line item identities split between two packages: **append 2 without deleting original package**.
- Same `slug+tracking_number+line_items`: **idempotent; no duplicate write**.
- An already claimed Woo line ID reused by a second package: **conflict**.

**Material business limitation:** A single Woo order line with quantity **2** physically fulfilled across **two different parcels** (qty 1 + qty 1, same `woocommerce_line_item_id`) triggers the current overlap fail-closed check, even though it is a legitimate fulfillment possibility. Existing validation checks each package quantity against the full remote line quantity and rejects *any* cross-package overlap; it does not currently compare the **cumulative sum of quantities across packages**. Do not silently remove this guard: a safe future extension needs aggregate quantity accounting, unique package identity and concurrency/idempotency tests. Until then, **same-line split-package auto-write is not supported**; route to review/manual exception with no remote overwrite.

Out-of-order confirmations, legacy tracking collisions, carrier slug ambiguity and cross-connection order references also require fail-closed audit at release.

## 4. Status and customer-communication risks

ERP `WooCommerceTrackingOutboundService` **also triggers `WooCommerceOrderStatusOutboundService::pushOne`** on successful or already-completed tracking outbox records. This is not a metadata-only sync. Resulting Woo status transitions can cause customer emails or downstream commerce events and must be explicitly sandboxed before any live canary.

Dev default safety MU prevents public checkout and outbound email; no active temporary checkout permit; Woo outgoing webhook inventory is empty in earlier Dev checks. **None of those alone establish total isolation** for an ERP-originated REST PUT, AfterShip third-party background plugin behavior or Jetpack/WooPayments events.

Dev-only synthetic Woo order **#39921** is a `checkout-draft` with no product lines, no ERP external reference and no shipment; it **cannot** serve as a valid ERP Tracking Outbound Canary. Do not edit #39921 or #39920 to fabricate a fulfillment test.
