# G6.2.5 — Shell Profiles & Assignment

Status: frozen requirement, implement immediately after G6.2.

## Goal
BeYourLover V3 must support multiple assignable Header/Footer profiles. Header and Footer are not one global hardcoded pair.

## Canonical profiles
- `global`: default site shell.
- `commerce`: Shop / Category / Product focused shell.
- `editorial`: Blog / Article / Editorial focused shell.
- `landing`: campaign / paid-traffic landing shell, minimal distraction.
- `utility`: Account / Support / selected transactional utility surfaces where a reduced shell is appropriate.

## Assignment precedence
1. Per-page/post/product explicit override.
2. Template/content-type assignment.
3. Global default.

Header and Footer are assigned independently, so a page may use one Header profile and another Footer profile.

## Admin UX
Add a `Header & Footer` tab under BYL V3 Settings. It must allow global defaults plus assignments for Homepage, Shop/Category, Product, Blog archive, Blog post, Landing Page, Support/Docs and Utility surfaces. Individual content may override with `Use default` or a named profile.
## Tesla-inspired interaction direction
Tesla.com is a reference for restraint and interaction discipline, not a source to copy. BeYourLover keeps Poppins, canonical brand red `#9B3749`, the canonical `BeYourLover` wordmark casing, its own navigation and its own iconography.

Target behaviors:
- Low-height, visually quiet Header; minimal borders/shadows.
- Optional transparent/overlay Header over eligible hero sections; solid surface after scroll.
- Primary navigation stays compact; utility actions remain Search / Account / Cart where relevant.
- Mobile uses one clear drawer/navigation state rather than stacked menus.
- Footer is sparse and purpose-driven; avoid legacy mega-footer density.
- Landing profile removes non-essential navigation while preserving trust/legal/support access.
- Commerce and Editorial profiles may have different menus, context navigation, utility density and footer link groups.

## Architecture rule
Profiles are code-owned presentation templates with data/config assignments; Settings selects profiles but does not become a page-builder. WordPress menu content remains canonical where a profile exposes navigation. Shoptimizer runtime must not be required.

## G6 integration
G6.3 Product consumes `commerce`; G6.4 Blog consumes `editorial`; campaign/landing templates consume `landing`. Existing G4 Global Shell becomes the first `global` profile instead of remaining a singleton shell.## Mega Menu and Mobile Navigation Contract
- Desktop `global` / `commerce` profiles support Tesla-inspired full-width Mega Menu panels anchored below the Header, driven from canonical WordPress menu trees rather than hardcoded links.
- Mega Menu may mix grouped links, featured destinations and optional category/product imagery, but must stay visually restrained and low-chrome.
- Open/close behavior must support pointer hover intent, click, keyboard focus, `Escape`, outside click and `aria-expanded`; reduced-motion users receive instant/minimal transitions.
- `editorial` may use a lighter discovery Mega Menu; `landing` defaults to no Mega Menu unless explicitly assigned.
- Mobile does not compress the desktop Mega Menu. It uses a full-height layered navigation: primary level -> child level -> back, with large touch targets, body-scroll lock and persistent utility actions where relevant.
- Mobile navigation must preserve hierarchy, return position and active state; no hover dependencies, nested accordions inside nested accordions, or horizontal overflow.
- Header profile settings select the WordPress menu source and navigation pattern; content remains editable in WordPress menus while presentation remains V3-owned.
- Responsive acceptance includes Desktop Mega Menu and 390px mobile nested-navigation UAT, not only the closed Header state.
