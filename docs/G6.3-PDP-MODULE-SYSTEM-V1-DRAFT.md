Status: DRAFT — Owner module-framework approval required before implementation.

Scope: BYL V3 Product Detail content architecture only. Production untouched.

## 1. Governing principle

A product page is not free-form editorial HTML. It is a composition of approved reusable modules.
The Woo purchase layer remains fixed and separate from the storytelling module stack.
Each content module owns its markup, responsive layout, media rules and allowed interactions.
Product editors replace content/configuration; they do not redesign layout per product.

Architecture:
1. Commerce Core — fixed Woo gallery / price / variation / CTA / stock / reviews contract.
2. Content Modules — approved reusable PDP modules, composed per product.
3. Interaction Primitives — shared gallery, tabs, modal, reveal, media and sticky-nav behavior.

## 4. Apple implementation patterns to learn from

Observed on the current public MacBook Air page and assets:
- declarative component binding through HTML data attributes rather than per-section bespoke scripts;
- shared horizontal scroll galleries with focus management;
- responsive picture/media with static fallback and lazy-loading boundaries;
- small scroll-triggered headline/reveal motion instead of full-page animation dependency;
- color/variant galleries, tabbed galleries and modals as shared interaction primitives;
- sticky local navigation for long product stories;
- comparison/upgrade experiences treated as a reusable decision-support pattern.

BYL should learn the architecture and interaction discipline, not copy Apple's code, copywriting or visual identity.

## 5. Shared interaction primitives (not counted as modules)

P01 ResponsiveMedia — picture/video, desktop/mobile source, poster/static fallback, aspect-ratio contract.
P02 ScrollGallery — horizontal overflow, snap, arrows, keyboard/focus support, no globally coupled selectors.
P03 Reveal — IntersectionObserver-based small fade/translate with prefers-reduced-motion support.
P04 ToggleGallery — color/variant/tab switcher with accessible state.
P05 Disclosure — accordion/expandable card and modal primitives.
P06 ChapterNav — sticky section navigation with active-section tracking.
P07 MediaLifecycle — lazy-init/pause offscreen media; never unconditional autoplay with sound.
## 6. Source-code rules for V1

Product content must never inject theme CSS/JS files or module-level <style>/<script> blocks.
Numeric classes such as section1/section11 are migration inputs only, not the new API.
Each module receives typed content/configuration and is rendered by the V3 theme.
Module CSS is namespaced; module JS is initialized only inside its own root element.
Shared interactions are imported once and configured declaratively with data attributes.
Below-fold media is lazy; responsive media always has a stable aspect ratio and fallback.
Mobile is an authored layout contract, not a desktop stack produced automatically.
No module may depend on Shoptimizer DOM, CommerceKit tab DOM or globally scoped Swiper selectors.

Proposed composition shape:
`Commerce Core -> [M01, M02, ... optional approved modules in product-defined order] -> Reviews/Related platform layer`.

All module design, implementation, and later maintenance are governed by `docs/BYL-WEB-DESIGN-UAT-GOVERNANCE-V1.md`.

Required sequence:
1. Desktop design draft → Owner PASS.
2. Mobile design draft → Owner PASS.
3. Only then implement.
4. Open the implemented result on the CN Mac.
5. Run Desktop + Mobile implementation UAT.
6. Mobile is the final acceptance priority.
7. LOCK only after both implemented views PASS.

Desktop approval alone is never sufficient for final module acceptance.
